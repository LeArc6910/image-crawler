# 개발 계획서: 암호화 이미지 보관소 + 모바일 PWA 뷰어

- 저장소: **Cloudflare R2** (S3 호환, 다운로드 무료, 무료 10 GB/월)
- 뷰어: **PWA** (휴대폰 브라우저에서 복호화, 홈 화면 설치)
- 원칙: 이미지·메타데이터·썸네일·목록은 모두 **기기 안에서만** 복호화한다. R2·호스팅·중계 어디에도 평문이나 키가 가지 않는다.

## 1. 목표 구조

```
[PC] image-crawler                         [R2 버킷]                         [휴대폰] PWA
 crawl ─► 이미지 암호화  ───────────────►  ab/<name>.bin        (원본)
       ─► 썸네일 생성·암호화 ────────────►  thumbs/cd/<name>.bin (썸네일)
       ─► 목록(인덱스) 암호화 ───────────►  index/<id>.bin       (목록 조각)
                                                  ▲
                         읽기 전용 키 + CORS      │  S3 서명 요청(GET/LIST)
                                                  └──────────── 인덱스 → 썸네일 → 원본 순으로
                                                                받아서 WebCrypto로 복호화
```

## 2. 데이터 형식 (v2)

| 객체 | 경로 | 내용 | 패딩 |
|---|---|---|---|
| 원본 | `<prefix>/ab/<name>.bin` | 이미지 + 메타데이터(출처 URL, 파일명, 형식, 수집 시각) | 64 KiB |
| 썸네일 | `<prefix>/thumbs/cd/<thumb>.bin` | 최대 320px WebP | 4 KiB |
| 인덱스 조각 | `<prefix>/index/<시각>-<난수>.bin` | 이미지 목록(JSON): 원본·썸네일 이름, 사이트, 파일명, 크기, 가로세로, 수집 시각 | 4 KiB |

- `name` = HMAC-SHA256(이름 키, 원본 내용), `thumb` = HMAC-SHA256(이름 키, `"thumb:" + name`)
  → 업체는 어떤 썸네일이 어떤 원본의 것인지도 알 수 없다.
- 암호문: `ICV2 | nonce(12) | AES-256-GCM(header | metadata | content | padding)`
- **v2의 AAD = `ICV2|<종류>|<이름>`**: 악의적인 서버가 암호문을 서로 바꿔치기(썸네일↔원본, A↔B)해도 복호화가 실패한다.
  (2024년 ETH 취리히 연구에서 상용 E2EE 서비스들이 당한 공격 유형 대응)
- v1(`ICV1`) 암호문은 계속 복호화 가능 (하위 호환).
- 인덱스는 **추가 전용 조각**으로 쌓는다. 크롤링할 때마다 새 조각을 올리므로 동시 수정 충돌이 없고,
  뷰어는 `index/` 아래 조각을 모두 받아 합친다. 조각이 많아지면 나중에 병합(compaction).

### Phase 1 — 크롤러: 뷰어가 쓸 데이터 만들기 (최우선)

뷰어는 이 데이터가 있어야만 만들 수 있고, 형식이 정해진 뒤에 바꾸면 이미 올린 데이터를 다시 올려야 하므로 가장 먼저 한다.

| # | 항목 | 내용 | 상태 |
|---|---|---|---|
| 1.1 | 저장소 계층 정리 | 키(경로) 기반 API로 바꿔 원본·썸네일·인덱스를 한 버킷에 구분해 저장 | ✅ |
| 1.2 | 암호 형식 v2 | 종류·이름을 AAD에 묶어 바꿔치기 방지, 객체별 패딩 크기, v1 복호화 유지 | ✅ |
| 1.3 | 썸네일 생성 | Pillow로 320px WebP, EXIF 회전 보정, 애니메이션은 첫 프레임, 실패 시 썸네일 없이 진행 | ✅ |
| 1.4 | 암호화 인덱스 | 크롤링 중 100개마다·사이트마다 인덱스 조각 업로드 | ✅ |

| 1.7 | JS 복호화 코어 | PWA가 쓸 `pwa/js/vault.js`(WebCrypto). Python이 만든 암호문을 Node로 푸는 교차 테스트 | ✅ |

**Phase 1 검증 결과** (위키백과 문서 1개 실제 크롤링, 로컬 저장소)

- 원본 93개 저장, 썸네일 90개(SVG 3개는 썸네일 없음), 인덱스 조각 1개
- 갤러리 표시에 필요한 데이터: 인덱스 65 KB + 썸네일 1.4 MB ↔ 원본 전체 12 MB
- `pwa/js/vault.js`(Node의 WebCrypto)로 93개 전부 복호화 성공, 썸네일을 원본 자리에 넣은 바꿔치기는 거부됨
- 남은 확인: 실제 R2 버킷에서 업로드·`cors` 명령 동작 (계정 필요)

**Phase 2 검증 결과**

- 헤드리스 Chromium(휴대폰 화면 크기)에서 전체 흐름 자동 테스트: 연결 → 틀린 비밀번호 거부 → 갤러리(썸네일 9 + SVG 자리표시 1)
  → 사이트 필터 → 원본 보기·다음 → 잠금 → 새로고침 후 비밀번호로 재잠금 해제, 콘솔 오류 0
- 저장소는 S3 호환 모의 서버 + R2처럼 CORS 규칙을 평가하는 중계로 대체. `cors` 명령이 등록하는 규칙으로 브라우저 요청이 통과함을 확인
- 남은 확인: 실제 R2·실제 휴대폰(특히 iOS Safari의 카메라 QR 스캔, 홈 화면 설치)

## 4. R2 설정 절차 (Phase 1 기준)

1. Cloudflare 대시보드 → R2 → 버킷 생성 (공개 접근 **끔**)
2. R2 API 토큰 두 개 발급
   - 크롤러용: 해당 버킷 **Object Read & Write**
   - 휴대폰용: 해당 버킷 **Object Read only** (Phase 2에서 사용)
3. `config.toml`
   ```toml
   [storage]
   backend = "s3"
   [storage.s3]
   bucket       = "image-vault"
   endpoint_url = "https://<ACCOUNT_ID>.r2.cloudflarestorage.com"
   region       = "auto"
   ```
4. 크롤러용 토큰을 `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` 환경변수로 지정
5. PWA 주소가 정해지면 `image-crawler cors --origin https://<사용자>.github.io`
   (토큰에 버킷 설정 권한이 없으면 대시보드 → 버킷 → Settings → CORS Policy에서 같은 내용 등록)

## 5. 위험 요소와 대응

| 위험 | 대응 |
|---|---|
| PWA 코드를 내려주는 곳이 코드를 바꿔 키를 빼돌림 | 저장소(Cloudflare)와 다른 회사(GitHub Pages)에서 배포, 외부 스크립트 없음, CSP, service worker 캐시 (3.2) |
| 휴대폰 분실 | 키는 비밀번호로 잠근 상태로만 저장, 자동 잠금, 휴대폰엔 읽기 전용 R2 토큰만 |
| 휴대폰 키 유출 | 휴대폰엔 복호화 키만 전달(이름 키·쓰기 권한 없음). 유출 시 R2 토큰 폐기 |
| 악의적 서버의 바꿔치기 | v2 AAD 바인딩 (1.2) |
| iOS가 PWA 저장 데이터 삭제 | 키 다시 가져오기(QR)를 쉽게 유지 |
| R2 무료 한도 초과 | 크롤러 요청 계량·차단 (1.8~1.11), 썸네일 우선 로드·원본은 탭할 때만, PWA 요청 보호 (3.7), Cloudflare 예산 알림 |
| 형식 변경으로 재업로드 | 형식 버전 표기(ICV1/ICV2, 인덱스 `v`), `reindex`로 보충 |
