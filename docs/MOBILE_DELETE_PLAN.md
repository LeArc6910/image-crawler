# 모바일 이미지 삭제 방안 (보류 — 사용자가 다시 요청하면 진행)

작성: 2026-11-02. 사용자 요청으로 정리만 해 두었고 아직 구현하지 않았다.
다음 세션은 이 문서와 [HANDOFF.md](HANDOFF.md)를 읽고, 사용자에게 방식(A/B/C)을 확인한 뒤 시작한다.

## 1. 목표

휴대폰 뷰어(PWA)에서

- 사진 한 장 삭제 (원본 보기 화면의 "삭제")
- 폴더(앨범) 통째로 삭제 (폴더 길게 누르기 또는 폴더 화면의 메뉴)

삭제 = 원본·썸네일 객체를 R2에서 지우고 목록(인덱스)에서 뺀다. 크롤러가 같은 이미지를 다시 받아 오지 않아야 한다.

## 2. 제약 (Cloudflare 공식 문서, 2026-10 확인)

- 휴대폰에는 지금 **읽기 전용 토큰**(Object Read only, `image-crawler` 버킷만)만 있다. 삭제하려면 어딘가에 쓸 수 있어야 한다.
- R2 API 토큰 권한은 Admin Read & Write / Admin Read only / Object Read & Write / Object Read only 네 가지뿐.
  Object 권한은 **버킷 단위로만** 범위를 좁힐 수 있다. "삭제만", "특정 폴더(prefix)만" 같은 장기 토큰은 없다.
- 경로·동작 단위 제한은 **임시 자격 증명**(Temporary Credentials, local signing의 `actions`/`prefixes`)에만 있고,
  이건 부모 토큰을 가진 서버가 매번 발급해야 한다 → 서버 없는 지금 구조에는 맞지 않는다.

## 3. 방식 비교

| | A. 삭제 요청함 (추천) | B. 휴대폰에 쓰기 권한 | C. 대화로 요청 |
|---|---|---|---|
| 방식 | 작은 버킷 `image-crawler-inbox`를 더 만들고, 휴대폰에는 **그 버킷에만** 쓰는 토큰을 준다. 휴대폰은 암호화한 삭제 요청을 넣고, 크롤러가 다음 실행 때 실제로 지운다 | 휴대폰 토큰을 `image-crawler` 버킷의 Object Read & Write로 바꾼다 | 앱 수정 없이 대화에서 "이 앨범 지워줘" → 클라우드 세션이 `delete` 명령 실행 |
| 휴대폰 화면 | 즉시 사라짐 (요청함을 읽어 숨김) | 즉시 삭제 | 다음 새로고침 때 |
| 실제 삭제 | 다음 크롤링 때 또는 "삭제 반영해줘" | 즉시 | 요청할 때 |
| 연결 정보+비밀번호 유출 시 | 사진 보기 + 삭제 **요청**까지. 대량 요청은 크롤러가 멈추고 확인 | **버킷 전체 삭제·덮어쓰기 가능** | 영향 없음 |
| 사용자 할 일 | 버킷·토큰·CORS → `viewer-export` 다시 → QR 다시 | 토큰 발급 → `viewer-export` 다시 → QR 다시 | 없음 |

추천은 A: 휴대폰 쪽 보안 수준(읽기 전용)을 유지하면서 화면에서는 바로 지워진다.

## 4. A안 설계

### 4-1. 사용자 준비 (Cloudflare 대시보드)

1. R2 → 버킷 만들기: `image-crawler-inbox`
2. API 토큰 (휴대폰용 2번째): **Object Read & Write**, 버킷은 `image-crawler-inbox`**만**
3. 크롤러 토큰이 inbox도 읽고 지울 수 있게: 기존 크롤러 토큰의 버킷 목록에 inbox 추가 (또는 새 토큰 → 클라우드 환경 변수 교체)
4. inbox 버킷 CORS: `https://learc6910.github.io`에 `GET`, `HEAD`, `PUT` 허용
   (헤더: `authorization`, `x-amz-date`, `x-amz-content-sha256`, `content-type`)
5. PC에서 `image-crawler viewer-export` 다시 (inbox 토큰도 묻게 바뀜) → 휴대폰에서 QR 다시 스캔

### 4-2. 삭제 요청 형식

- 위치: `image-crawler-inbox` 버킷의 `delete/<시각>-<난수>.bin`
- 내용: 기존 암호 형식 그대로(`ICV2`, AES-256-GCM, Padmé). 종류(kind) `request`, 이름 = 객체 키의 시각-난수 부분 (AAD로 묶임)
  ```json
  {"v": 1, "objects": ["<원본 이름>", ...], "reason": "photo" | "folder", "folder": "<page_url>", "at": "<ISO 시각>"}
  ```
- 휴대폰은 암호화 키(encryption key)를 이미 갖고 있으므로 같은 키로 봉인한다. 크롤러는 마스터 키에서 같은 키를 유도해 연다.
  키가 없는 사람은 요청을 만들 수 없다 (열리지 않는 요청은 무시하고 지운다).

### 4-3. 크롤러

- `image-crawler apply-deletes` 명령 + `crawl` 시작할 때 자동 실행
- inbox 목록 → 요청 열기 → 대상 객체 모아서:
  - **안전장치**: 한 번에 500개(설정 가능) 넘으면 지우지 않고 멈춤 → `apply-deletes --yes`로 확인 후 진행
  - 원본 `ab/<name>.bin`, 썸네일 `thumbs/…` 삭제 (R2의 DeleteObject는 무료 작업)
  - 인덱스에 **삭제 표시 항목** `{"object": name, "deleted": true}` 추가. "같은 객체는 나중 항목이 이긴다" 규칙(이미 구현됨)으로
    목록에서 빠진다. `compact`는 삭제 표시된 객체를 아예 뺀다
  - 상태 DB: `objects`에서 지우지 말고 `deleted` 표시 → 같은 URL·같은 내용을 다시 받지 않음 (`images.status = 'deleted'`)
  - 처리한 요청은 inbox에서 삭제
- 앨범 완료 기록(`albums`)은 그대로 둔다 (지운 앨범을 다시 받지 않게)

### 4-4. 휴대폰 뷰어

- `vault.js`: 봉인(seal) 함수 추가 (지금은 열기만 있음). Python과 교차 테스트(`tests/js/check_vault.mjs`)에 추가
- `s3.js`: PUT 서명 (본문 SHA-256), inbox용 두 번째 클라이언트
- 연결 정보(bundle) 형식에 inbox 엔드포인트·토큰 추가 → 버전 올림 (`ICVIEW2`), 옛 형식도 계속 읽기 (삭제 메뉴만 숨김)
- 화면: 원본 보기의 "삭제", 폴더의 "폴더 삭제" → 확인 대화상자(폴더는 장수 표시) → 요청 PUT → 즉시 숨김
- 갤러리 불러올 때 inbox의 대기 중 요청도 읽어 숨김 ("삭제 대기 N장" 표시)
- 요청 폭주 방지(`RequestBudget`)에 PUT 포함

### 4-5. 테스트

- Python: 요청 봉인/열기, 안전장치, 삭제 표시 후 `read_index`·`compact`, 재크롤링 시 다시 받지 않음
- PWA E2E(moto + r2_like 중계): 삭제 → 즉시 숨김 → `apply-deletes` → 새로고침 후에도 없음, 틀린 키로 만든 요청 무시

## 5. B안 / C안 메모

- B안: 구현은 가장 단순(뷰어에서 DeleteObject + 인덱스 삭제 표시 PUT). 하지만 연결 정보와 비밀번호가 함께 유출되면
  저장소 전체를 지우거나 가짜 이미지로 덮어쓸 수 있다. 지금까지 지켜 온 "휴대폰은 읽기 전용" 원칙이 깨진다.
- C안: 4-3의 삭제 로직(`delete --object/--folder/--site`)만 만들고 대화로 실행. A안을 만들 때도 이 로직은 그대로 쓰인다
  → A안의 첫 단계로 C안을 먼저 만들어도 된다.

## 6. 같은 요청함으로 할 수 있는 것: 휴대폰에서 수집 요청 (검토만)

사용자 질문(2026-11-02): PWA에 "이미지 수집" 메뉴 → 사이트별 진행 상황 표시 → 수집량 정하고 "수집" 버튼.

- **진행 상황 표시는 쉽다**: 크롤러가 실행 끝에 사이트별 진행(`progress`)을 암호화한 `status/progress.bin`으로 올리면
  휴대폰은 지금의 읽기 전용 토큰으로 읽어 보여 줄 수 있다.
- **수집 버튼은 "실행할 곳"이 필요하다**: 휴대폰 브라우저는 크롤러를 돌릴 수 없고, 지금 크롤러는 사용자가 요청할 때
  클라우드 세션에서만 돈다. 버튼이 A안의 요청함에 "수집 요청"을 넣고, 무언가가 그걸 주기적으로 확인해 실행해야 한다.
  | 실행할 곳 | 장점 | 단점 |
  |---|---|---|
  | Claude 예약 작업 (주기적으로 새 세션) | 지금 환경 그대로, 키도 이미 있음 | 확인할 때마다 세션 사용량, 요청 후 시작까지 지연(주기만큼) |
  | GitHub Actions (cron 또는 휴대폰이 workflow_dispatch) | 무료, 빨리 시작 | 저장소가 공개라 **실행 로그가 공개됨**(사이트·앨범 이름 노출 위험), GitHub 이용 정책상 프로젝트와 무관한 작업 용도는 문제 소지, 키를 GitHub Secrets에 둬야 함 |
  | Cloudflare Containers/Workers | 버튼 즉시 실행 | 유료(Workers Paid), 키와 저장소가 같은 회사에 모임 |
- 결정은 사용자에게: 진행 상황 표시만 먼저 할지, 실행 방식까지 정할지.
